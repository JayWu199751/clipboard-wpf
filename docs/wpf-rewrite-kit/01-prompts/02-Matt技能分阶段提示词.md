# Matt 技能：分阶段可复制提示词

依据用户指定的 ask-matt 技能工作流整理。先发总提示词建立上下文，再选当前阶段的正文；不是把下面所有段落一次塞给 agent。已在原机器发现的技能包括 ask-matt、setup-matt-pocock-skills、grill-with-docs、domain-modeling、prototype、to-spec、to-tickets、implement、implement-spec、tdd、code-review、handoff、retro；其他环境先核对文件。

## A. 环境与工作流准备

> 使用 `ask-matt` 选择 ClipboardTool C# + WPF 重写的流程，然后读取 `setup-matt-pocock-skills`，检查而不是直接覆盖已有 tracker、GLOSSARY、ADR 和 agent 指令。当前交付包是 `docs/wpf-rewrite-kit/`，项目范围由其中的功能规格确定。先核验 git 状态、可用 .NET SDK 与 Windows 工具链，提交已有可回退基线；给出本地文件 ticket 的落地目录与检查命令。用户尚未授权发布远程 issue 或消息，优先用本地文件承载。完成标准：能定位所有输入资料，工作流前置条件满足或缺失清楚列明，不直接实现一整套产品。

## B. 澄清真正待决的问题

> 使用 `grill-with-docs`，底层使用 `domain-modeling`。先完整读总提示词引用的事实源，把 F01–F48 对照到当前源码；已知功能不要问我第二遍。重点澄清 Windows 支持范围、内存实测门槛、发布方式/安装体积、字体分发、旧安装身份与切换方式。把确定术语落到 GLOSSARY，把难回退决策落到 ADR；每次问题说明它会改变哪个方案和哪项验收。完成标准：全部事实有出处、每个真正未知有结论或明确试验、用户的 C# + WPF 路线与功能等价要求已进入规格，不能把自己的默认预算写成用户确认。

## C. 高风险可运行试验

> 使用 `prototype` 回答一个具体问题：[填入例如：WPF 浏览态不抢焦点，进入搜索并退出后能否把粘贴送回原控件]。先列成功/失败判据，再做最小可运行 Windows 试验。使用隔离存档与虚构内容，保留试验代码、观测日志与结果。现有 HTML 原型只展示 HUD，不能证明 Win32 焦点、UIPI、DIBV5、开机登录或混 DPI。每次只解决一个风险，结论引用到 ADR/规格；换目录用 `handoff`，不要原样把试验代码当生产实现。完成标准：有复现命令、观测证据、约束结论与未覆盖项。

其他试验分别做：DIBV5 alpha 与旧 PNG 去重；变高卡片 Recycling 下选中项完整可见；圆角穿透+搜索可交互；跨完整性单实例通信；透明 WPF 面板常驻与图片缓存的内存构成。

## D. 合成规格

> 使用 `to-spec`，合成已经完成的澄清、平台试验与 ADR，形成 C# + WPF 可实现规格。用 `docs/wpf-rewrite-kit/02-spec/` 的事实作为基准，给出 F01–F48 覆盖映射、领域/应用/基础设施/UI 边界、存档读写契约、模式与粘贴顺序、异常路径、性能测量与真机验收。旧版实现细节中仅 Tauri 特有机制标为替换策略；其用户结果和平台安全边界保留。完成标准：每项功能都能找到验收与责任模块，全部已决事项写入，不留「之后再考虑」的隐藏依赖。

## E. 拆纵向 ticket

> 使用 `to-tickets`，输入上一阶段的最终规格与 `05-validation/01-验收矩阵.md`。按端到端可运行切片拆票，每票声明阻塞边、功能编号、允许改动范围、最小红绿测试、真机操作和完成判据。首票必须能运行 WPF HUD，下一票就串通文字通知→存档→卡片→安全粘贴→停靠；不是先横向写完所有服务。高风险试验先阻塞依赖票，图片可以在文字链路稳定后并入。本地每票一个文件，推荐 `.scratch/wpf-rewrite/issues/`。完成标准：覆盖全部功能，依赖图无循环，每票从 fresh context 能独立开始且知道如何证明完成。

## F. 单票实现（默认）

> 使用 `implement` 实现 ticket [路径/编号]；读取它引用的最小事实源，然后用 `tdd` 按一条行为红→绿推进。在每票开始检查 git 状态，保护已有工作。领域测试经 public interface/端口断言真实行为，不能只 mock WPF 框架或复制实现。判定不依赖 UI，窗口/剪贴板/任务效果保持正确线程与所有权；相关功能覆盖到验收表。完成后 `code-review` 同时审 Standards 与 Spec，修复发现，执行零警告构建与相关测试，同步文档，中文提交。UI/提权未测的地方写待真机验证。单票完成后输出可继续票与阻塞关系；下一票建议新会话重新引用自身 ticket。

## G. 用户选择整图并行实现时

> 使用 `implement-spec` 按规格及 ticket 阻塞图在集成分支推进。只有阻塞已完成的前沿可并行；每个实现者使用 `tdd`，共享存档/窗口/消息线程/模式的文件必须明确所有权与集成顺序。功能等价和零警告门槛不变，结束后在集成分支做一次两轴 `code-review` 与全量验收。没有真机证据的条目不能标完成；预算也不能当成实测。开始前先确认本环境可用的 agent 工作流与技能文件。

> 对最终实现使用 `code-review`，按 `05-validation/01-验收矩阵.md` 做逐项功能审计；自动测试、Windows 真机与性能对比独立报告。验证新旧存档往返、提权/普通目标粘贴、开机第一次三路呼出、DPI/任务栏/托盘主题、安装升级卸载与备份回退。把每项结果链接到证据，再形成可review的切换操作。最后用 `retro` 总结应该加入环境/工具链/AGENTS 的检查规则；未经用户验收的真人 GUI 步骤保留待验证。完成标准：全部范围有结论，关键失败无遗漏，性能有原版与新版同口径数据，回退能执行。
